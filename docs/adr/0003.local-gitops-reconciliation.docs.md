# ADR 0003: Reconcile the local Kubernetes environment with Argo CD

## Status

Accepted

## Context

[ADR 0002](0002.local-kubernetes-parity.docs.md) establishes Kind as the authoritative local integration environment and assigns its desired workload state to `gitops/`. It leaves the local reconciliation mechanism, Git-label promotion policy, and initial dependency set undecided.

The local workflow needs continuous reconciliation from Git without introducing a different manifest-authoring model for each environment. BidPoint-owned workloads and third-party platform software have different distribution needs: the former need explicit environment variants, while the latter are commonly distributed as versioned Helm charts.

Using long-lived `local`, `dev`, `stage`, and `prod` branches for the organization monorepo would duplicate environment identity already expressed by owner-marked configuration files and GitOps overlays. It would also make promotion merge unrelated application, configuration, deployment, infrastructure, and documentation changes between divergent repository histories.

## Decision

Argo CD is the GitOps reconciler for `local`. It runs inside the Kind cluster in its own namespace and manages that cluster through its internal Kubernetes API endpoint.

The bootstrap sequence is intentionally imperative at its boundary:

1. A developer creates the Kind cluster.
2. A developer installs a pinned upstream Argo CD Helm chart.
3. Argo CD reconciles BidPoint workload state from `gitops/`.

Exact Kind node images, Kubernetes versions, and Helm chart versions are pinned in the [local bootstrap runbook](../runbooks/kubernetes-bootstrap.docs.local.md) rather than in this decision record. Whether Argo CD manages upgrades of its own installation after the initial bootstrap remains a separate decision.

Argo CD renders workload sources according to ownership:

- BidPoint-owned workloads use Kustomize bases with explicit `local`, `dev`, `stage`, and `prod` overlays.
- Third-party platform software uses pinned upstream Helm charts with BidPoint-owned values.
- Argo CD, rather than a separate Helm release process, owns the lifecycle of resources it renders from Helm charts.

Helm values and Kustomize overlays may contain only deployment state owned by `gitops/`, such as image references, replicas, resources, probes, and networking. Backend application behavior remains owned by `config/`, and secret values remain outside Git.

The monorepo keeps one authoritative `main` branch and uses short-lived feature branches. Environments are selected through explicit owner-marked configuration files and GitOps overlays, not long-lived environment branches. Spring Cloud Config uses `main` as its normal Git label; a developer may select a pushed feature branch temporarily to test unmerged local configuration. Promotion changes the explicit target-environment file or overlay through review on the same repository history.

The initial local image workflow loads locally built images into Kind. A local registry is not introduced until a demonstrated development need justifies it.

The initial local dependency set contains only the platform components required to prove the configuration path: Argo CD and Spring Cloud Config Server. Databases, message brokers, ingress, and observability components are added only when an implemented workload requires them.

When repository authentication is required, Argo CD and Config Server receive credentials through Kubernetes Secret references. A developer creates the initial local Secret values outside Git; the repeatable procedure belongs in a runbook. No credential is stored in a manifest, Helm values file, Kustomize overlay, or Spring configuration source.

## Consequences

- Local workload drift is detected and, when automated synchronization is enabled, corrected from Git.
- Recreating a lost local cluster requires creating Kind and bootstrapping Argo CD again before reconciliation can restore workloads.
- BidPoint applications retain readable Kubernetes bases and explicit environment differences without maintaining a packaging interface for single-repository consumers.
- Third-party software can follow its upstream chart lifecycle without copying its rendered manifests into the repository.
- Environment promotion stays visible in one Git history and cannot implicitly merge the entire monorepo between environment branches.
- Local configuration experiments must be committed and pushed before Config Server can serve them, including experiments that use a feature branch label.
- Loading images directly into Kind is a deliberate local-only delivery difference; remote environments will pull published images from a registry.
- A newly created local cluster requires its non-committed Secret values to be supplied again.
- Exact version pins, the Config Server source location, Argo CD self-management, remote Argo CD topology, and later runtime dependencies remain to be decided with their implementations.

## Alternatives considered

### Apply Kustomize output manually

Running `kubectl apply -k` would be a smaller bootstrap, but it would not continuously detect or correct drift and would leave the authoritative local path different from the intended GitOps workflow.

### Use Helm for every workload

Helm can render BidPoint workloads, but publishing a values interface and maintaining templates for applications consumed only by this monorepo adds packaging complexity without a current reuse requirement.

### Use Kustomize for every workload

Recreating third-party charts as owned manifests would transfer responsibility for tracking their resource sets and upgrade changes to BidPoint.

### Use one long-lived branch per environment

Environment branches are valid Spring Cloud Config labels, but using them for the entire monorepo would create four divergent copies of unrelated modules and duplicate the environment identity already present in filenames and overlays.

### Run local Argo CD outside the cluster

Argo CD is designed to reconcile Kubernetes from inside Kubernetes. Running its components on a developer machine would tie reconciliation to that process and introduce a local-only operating model.
