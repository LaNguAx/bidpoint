# BidPoint exclusions and open questions

Status: Canonical
Last validated: 2026-08-01

This register separates genuine future choices from baseline exclusions. An **Open** item needs evidence before selection; it is not a request to decide now. An **Excluded** item is deliberately outside the baseline and may be reconsidered only when its stated trigger is met. **Optional comparison** exercises are later learning work and cannot mutate the canonical target merely because they are evaluated.

## Genuine open choices

| Open choice | Why it remains open | Decide by | Decision criteria | Work blocked |
| --- | --- | --- | --- | --- |
| Frontend companion stack: framework, state, data fetching, testing, and design-system details | CSR is selected, but a frontend ecosystem would add dependencies and conventions before the browser product slice is implemented. | Before the first authenticated browser vertical slice needs client state, API caching, component testing, or visual-system conventions. | Compatible with CSR/SSE and token handling; maintainability; accessibility; testing story; bundle/developer ergonomics; fit with pnpm/Nx without weakening Maven authority. | Frontend application implementation, client test harness, and component-library conventions. Backend REST/SSE contracts are not blocked. |
| Payment provider and its sandbox/webhook contract | The provider must support stable payment-intent/idempotency identifiers, webhook signature verification, replay handling, and reconciliation after ambiguous requests. | Before payment-service provider adapter, real webhook contract tests, or any real payment smoke test. | Stable-key idempotency; lookup/reconciliation by provider key; webhook signature/replay guarantees; supported geography/currency; sandbox quality; operational/audit suitability; cost and secret-management fit. | Provider adapter, real payment lifecycle, webhook fixtures, and payment smoke evidence. No card data enters BidPoint while open. |
| Notification delivery provider and reconciliation contract | The worker needs externally verifiable idempotency after ambiguous delivery attempts; a local attempt record cannot prove whether the provider accepted delivery. | Before implementing a real provider adapter, credentials, provider contract tests, reconciliation runbook, or delivery smoke test. | Stable provider idempotency key; reconciliation/status lookup by the same key; unambiguous accepted/not-accepted outcomes; supported channels/regions; sandbox quality; delivery/audit evidence; cost, limits, and secret-management fit. | Provider-specific worker adapter and configuration, real provider fixtures, reconciliation automation/runbook, and external delivery smoke evidence. Local Kafka facts/outbox design is not blocked. |
| Schema registry: Apicurio locally and potentially remotely for parity versus AWS Glue Schema Registry | Event envelope/versioning is decided, but registry ownership and managed-service tradeoffs are not. | Before a registry is introduced into local or remote event publication/compatibility gates. | Compatibility mode; schema formats; local/remote parity; AWS integration; access model; operational overhead; migration/export path; CI compatibility checks. | Registry-backed serialization/configuration and registry-specific compatibility automation. | Timing and success criteria for later comparison exercises | Comparisons are useful only after the canonical path produces measurable behavior and a stable baseline. | At the corresponding roadmap milestone, after baseline acceptance evidence exists. | Hypothesis; bounded scope; baseline metric; operational cost; reversibility; learning value; proof that the trial will not become an undeclared platform dependency. | The optional experiments themselves, not the canonical stages. |

## Explicit exclusions from the baseline

| Excluded item | Rationale | Reconsider only when |
| --- | --- | --- |
| AWS API Gateway | Spring Cloud Gateway is the selected runtime application gateway, with ALB/WAF as the AWS front door. | A documented public-edge requirement cannot be met by ALB plus Spring Cloud Gateway and shows a clear ownership/cost/security benefit. |
| Eureka | Kubernetes Services and DNS already provide internal service discovery. | A non-Kubernetes runtime or a measured discovery need makes Kubernetes-native discovery insufficient. |
| Spring Cloud Kubernetes discovery server | Kubernetes-native DNS/service discovery avoids an extra discovery authority. | A supported, evidence-backed requirement needs behavior unavailable from Services/DNS alone. |
| Spring Cloud Stream initially | Explicit Kafka/RabbitMQ client contracts teach delivery semantics and avoid premature abstraction. | Baseline outbox, ordering, retry, and recovery evidence is complete and a bounded comparison demonstrates a net benefit without hiding those semantics. |
| Valkey as canonical managed Redis | Redis Cloud is the current managed Redis choice; Redis remains non-authoritative. | The staged ElastiCache/Valkey comparison produces better evidence on compatibility, cost, operations, and migration risk. |
| Karpenter initially | Managed node groups are the selected remote node-capacity baseline. | Measured node-capacity constraints persist after managed-node-group policy is tuned and Karpenter operational controls are accepted. |
| Istio sidecars | The staged mesh direction is ambient, avoiding sidecar lifecycle complexity in the baseline. | A supported requirement cannot be met by ambient mode and a sidecar operational model is justified with security/performance evidence. |
| MinIO and AIStor | S3Mock is the deliberately narrow local S3 compatibility double. | A specific S3-contract gap blocks learning and a comparison proves a second storage product is worth its operational burden. |
| LocalStack OSS | The local target uses real protocol-focused components and scoped AWS smoke tests, not a broad cloud emulation baseline. | A bounded AWS integration need cannot be safely or economically covered by existing local doubles plus scoped smoke tests. |
| Promtail | Local logs flow through the OpenTelemetry Collector to Loki. | The selected collector pipeline cannot meet a demonstrated log-collection requirement and a replacement does not create dual ingestion ownership. |
| ingress-nginx | Pinned Traefik is the local cluster edge; ALB is the AWS edge. | A documented routing capability cannot be met by the selected front-door stack. |
| H2 | Testcontainers PostgreSQL is needed to prove PostgreSQL migrations, transactions, locking, and SQL behavior. | A narrowly isolated test has no persistence-semantic claim and H2 cannot be mistaken for integration evidence. |
| Legacy X-Ray SDK/daemon | OpenTelemetry/ADOT is the trace instrumentation and collection path. | AWS documents a necessary supported migration path that cannot be met through OpenTelemetry/ADOT and does not duplicate trace ownership. |
| Direct Jenkins production deployment | Jenkins builds and proposes Git desired-state changes; Argo CD performs reconciliation. | The GitOps control plane is unavailable in a bounded emergency procedure with separately authorized, audited, reversible controls. |
| OpenSearch on day one | Browse/filter remains a Core capability; full-text search is a staged derived view. | Core marketplace behavior, Kafka facts, and projection/recovery evidence are stable and search need is demonstrated. |
| Docker Compose as the canonical full environment | The learning target requires Kubernetes controllers, routing, readiness, scaling, delivery, and telemetry boundaries. | A narrowly scoped developer aid is separately accepted without claiming parity or replacing `core`/`platform`. |
| RabbitMQ Streams | RabbitMQ is selected for explicit targeted work to competing workers, while Kafka owns durable replayable facts. | A one-work-obligation stream requirement has evidence that the Kafka/RabbitMQ split cannot satisfy it. |
| Physical database per Modulith module on day one | Core modules require independent logical write boundaries, not premature operational database splits. | An extraction/evidence decision proves independent deployment, recovery, or scaling requires a physical split with no shared-writer transition. |
| Shared cross-service business models | Producer-owned contracts and owner APIs prevent cross-service implementation coupling. | A cross-cutting type can be proven mechanical rather than domain behavior and is accepted as a narrowly scoped shared library. |
| Environment branches | Same-repository GitOps uses environment directories on `main` and promotes an immutable image digest. | A governed promotion/audit requirement cannot be met by reviewed path-scoped changes on `main`. |
| Ansible | Terraform, Helm, Argo CD, and Jenkins Configuration as Code have explicit distinct ownership. | A gap remains after assigning an asset to those owners and Ansible can be introduced without creating dual mutable ownership. |
| Microservices solely for appearance | A service must have an independent consistency, scaling, failure, or integration responsibility. | Evidence demonstrates one of those responsibilities and records data, contract, operational, and migration consequences. |
| Frontend application-stack selection in current backend discovery | CSR establishes the boundary without selecting a UI ecosystem before it is needed. | The first browser vertical slice reaches the frontend decision gate listed above. |

## Optional comparison exercises, later only

| Comparison | Baseline held constant | Entry condition and evidence |
| --- | --- | --- |
| Debezium CDC outbox versus application relay | Transactional outbox, stable event identity, at-least-once consumer processing, and producer ownership. | Compare only after the application relay has measurable backlog/recovery behavior; assess failure modes, operational burden, ordering, and replay. |
| gRPC versus REST for one selected internal path | Public APIs stay REST and service ownership/data rules do not change. | Select one latency/streaming-sensitive internal path with a measured REST baseline and an explicit contract migration/rollback plan. |
| GitHub Actions versus Jenkins | Jenkins remains CI baseline; Argo CD remains the production reconciler. | Reproduce an equivalent bounded CI workflow and compare maintenance, agents, provenance, integration, and failure evidence. |
| ElastiCache/Valkey versus Redis Cloud | Redis remains acceleration/ephemeral coordination and never business authority. | Compare managed availability, compatibility, cost, operations, security, and migration/recovery without making the trial a data authority. |
| Karpenter versus managed-node-group scaling | HPA/KEDA behavior and managed node groups remain baseline capacity controls. | Use actual scheduling/capacity evidence and compare cost, disruption, security, and operational controls. |
| Schema registry options | Explicit event envelopes, versioning, stable IDs, and consumer compatibility remain baseline. | Evaluate Apicurio and AWS Glue only after compatibility test requirements and an event schema scope are defined. |
| SSE versus WebSockets if requirements change | SSE remains browser live-update baseline and REST remains command authority. | Require a documented bidirectional/live-interaction need that bounded SSE cannot meet, plus auth, reconnect, scaling, and recovery evidence. |
| Multi-region disaster recovery | Single-region target design and owner-local recovery remain baseline. | Start after backup/restore, replay, immutable deployment, and regional failure objectives are demonstrated; compare RPO/RTO, consistency, cost, and operational readiness. |

## Interpretation rules

Open and Optional comparison records do not authorize new dependencies, manifests, services, cloud resources, or claims that a capability exists. An exclusion is not an unresolved question. Any reconsideration must update the decision register, identify the affected detailed design documents, and use [official primary-source evidence](23-primary-sources.md) rather than search snippets or memory.
