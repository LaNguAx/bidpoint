# BidPoint decision register

Status: Superseded by [design-system 2.0](../2.0/README.md)
Last validated: 2026-08-01

This is the durable record of accepted target-design decisions. It describes no running application or provisioned platform. `Canonical` entries are the baseline a later implementation must preserve unless new evidence records the consequence of changing it. `Staged` entries are deliberate later increments, not day-one dependencies. `Open` entries are intentionally undecided and are detailed in [exclusions and open questions](22-exclusions-and-open-questions.md). Source and compatibility evidence is maintained in [primary sources](23-primary-sources.md).

## How to use this register

An entry has an identifier, a decision, status, rationale, consequences, and the detailed documents that define its contract. A status is not an implementation claim. In particular, “Canonical” means the selected target baseline, not that a dependency, manifest, image, account, or cluster exists in this repository.

## Product and topology

| --- | --- | --- | --- | --- | --- |
| ADR-001 | BidPoint is a real-time auction marketplace and distributed-systems reference platform with deliberately manageable business logic. | Canonical | Auctions create meaningful concurrency, recovery, ordering, and ownership pressure without needing a feature-complete commerce domain. | Correctness of bids, orders, payments, and recovery matters more than expanding the product catalog. | [01](01-project-thesis.md), [02](02-product-domain-and-capabilities.md) |
| ADR-002 | The authenticated browser application will use client-side rendering (CSR); frontend framework, state, data-fetching, test, and design-system libraries are not selected. | Canonical | CSR is sufficient to define browser/API and SSE contracts without prematurely choosing a frontend ecosystem. | Public and authenticated routes must support browser clients; no frontend package choice may be smuggled into backend discovery. | [01](01-project-thesis.md), [07](07-rest-sse-and-service-communication.md), [16](16-monorepo-and-repository-structure.md) |
| ADR-003 | `core-platform` is a Spring Modulith modular monolith, surrounded by focused services; BidPoint is not an all-microservices design. | Canonical | Profiles, catalog, listings, auction lifecycle, and orders initially benefit from cohesive evolution and local transactions. | Core boundaries must be verifiable; an extraction requires evidence of independent load, cadence, ownership, or failure isolation. | [03](03-architecture-overview.md), [04](04-core-platform-modular-monolith.md), [05](05-microservice-boundaries.md) |
| ADR-004 | The five Core modules are `profiles`, `catalog`, `listings`, `auctions`, and `orders`. | Canonical | They align with the bounded marketplace lifecycle and local consistency needs. | Each is the only writer of its logical schema; sharing a PostgreSQL deployment does not permit cross-module writes or joins. | [02](02-product-domain-and-capabilities.md), [04](04-core-platform-modular-monolith.md), [06](06-data-ownership-and-consistency.md) |
| ADR-005 | Surrounding deployables are exactly `api-gateway`, `bidding-service`, `payment-service`, `realtime-service`, `notification-service`, `notification-worker`, and staged `search-service`. | Canonical | Each has an independent public-edge, concurrency, provider, streaming, policy, worker, or search-indexing responsibility. | `api-gateway` owns application-edge concerns; bidding owns bids; payment owns provider state; realtime owns derived SSE; notification service owns policy; notification worker owns delivery attempts; search owns only derived full-text search when staged. | [03](03-architecture-overview.md), [05](05-microservice-boundaries.md) |
| ADR-006 | The staged search deployable is named `search-service`, never `search-indexer`. | Canonical | The service owns both indexing and the future REST query surface, not merely an indexing process. | Search remains a derived, non-authoritative OpenSearch view; initial browse/filter remains in Core. | [03](03-architecture-overview.md), [05](05-microservice-boundaries.md), [17](17-local-technology-stack.md) |

## Code, contracts, and data authority

| ID | Decision | Status | Rationale | Consequences and tradeoffs | Detailed contract |
| --- | --- | --- | --- | --- | --- |
| ADR-007 | Each Core module is one Maven JAR with `api/`, separately named `api/events/`, implementation `internal/`, and producer-owned `contracts/events/`; there are no separate API/implementation artifacts. | Canonical | A small predictable surface prevents internal persistence classes from becoming accidental public contracts. | Other Core modules compile only against `api/`; `api/events/` is for internal Spring Modulith events, while `contracts/events/` is the external Kafka wire contract. | [04](04-core-platform-modular-monolith.md), [08](08-kafka-events-and-transactional-outbox.md) |
| ADR-008 | Ordinary modules and services use familiar Spring MVC-style organization and split further only when complexity justifies it; Spring Cloud Gateway alone uses WebFlux. | Canonical | Conventional structure reduces ceremony while retaining a clear reactive boundary where the chosen gateway requires it. | Do not create arbitrary shared layers or capability trees. A future SSE implementation selects its streaming model during implementation without changing the gateway decision. | [04](04-core-platform-modular-monolith.md), [05](05-microservice-boundaries.md), [07](07-rest-sse-and-service-communication.md) |
| ADR-009 | External contracts are producer-owned; BidPoint has no shared business-domain model library. | Canonical | Ownership must remain explicit across module and service boundaries. | Shared Java libraries may contain cross-cutting mechanics only. Consumers use versioned REST contracts or producer-owned events, never another owner’s entities, repositories, tables, or internal DTOs. | [04](04-core-platform-modular-monolith.md), [06](06-data-ownership-and-consistency.md), [16](16-monorepo-and-repository-structure.md) |
| ADR-010 | A module or service is the sole writer of its owned data; there are no cross-service joins. Logical Core schemas may share one PostgreSQL deployment initially. | Canonical | Write authority is the consistency and recovery boundary. | Current cross-owner data comes through an API; lag-tolerant views use owner-local projections. A shared deployment does not create shared authority. | [06](06-data-ownership-and-consistency.md), [12](12-aws-production-platform.md) |

## Communication and reliability

| ID | Decision | Status | Rationale | Consequences and tradeoffs | Detailed contract |
| --- | --- | --- | --- | --- | --- |
| ADR-011 | REST is used for synchronous APIs, SSE for browser live updates, Kafka for durable business facts, and RabbitMQ for targeted work. | Canonical | Each mechanism has a distinct delivery and consistency purpose. | Kafka is replayable fan-out, not request/reply; RabbitMQ is a competing-worker work channel, not a fact store; SSE updates are not authoritative command results. | [07](07-rest-sse-and-service-communication.md), [08](08-kafka-events-and-transactional-outbox.md), [09](09-rabbitmq-jobs-and-notifications.md) |
| ADR-012 | Producers use transactional outboxes; consumers use durable inbox/deduplication or equivalent stable-ID processing; delivery is at least once and never claimed end-to-end exactly once. | Canonical | A local transaction can atomically retain authoritative state and publication intent, but a relay can still redeliver. | Relays, consumers, retries, DLQs/quarantine, replay, and audit must preserve stable identities and make partial failure visible. | [06](06-data-ownership-and-consistency.md), [08](08-kafka-events-and-transactional-outbox.md), [09](09-rabbitmq-jobs-and-notifications.md) |
| ADR-013 | Auction Kafka facts are partitioned by `auctionId`; hot-partition tests and measured mitigation are mandatory. | Canonical | Per-auction ordering protects lifecycle/projection reasoning. | There is no global order, and a popular auction can concentrate load. Mitigation may not violate the per-auction ordering requirement. | [01](01-project-thesis.md), [05](05-microservice-boundaries.md), [08](08-kafka-events-and-transactional-outbox.md), [15](15-testing-and-quality.md) |
| ADR-014 | Notifications flow as fact -> decision -> durable local outbox -> RabbitMQ job -> idempotent worker. | Canonical | Policy and provider execution fail differently and need separate durable evidence. | `notification-service` never calls the provider directly. Unknown provider outcomes are quarantined and reconciled before a controlled retry with the same stable key. | [03](03-architecture-overview.md), [09](09-rabbitmq-jobs-and-notifications.md) |

## Edge, security, and local platform
| ADR-029 | The only authoritative order trigger is auctions-owned `AuctionClosed`, committed atomically with `CLOSED` through durable Spring Modulith event publication after Bidding fence acknowledgement. | Canonical | Bidding owns final bid outcome; auctions owns lifecycle closure, and orders must not race ahead of it. | The REST acknowledgement and bidding outcome are audit/projection input only. `orders` consumes after commit and deduplicates by event/auction identity; the same `AuctionClosed` may be externalized to Kafka with the same identity. | [03](03-architecture-overview.md), [04](04-core-platform-modular-monolith.md), [08](08-kafka-events-and-transactional-outbox.md) |

| ADR-019 | BidPoint is a future Nx + Maven monorepo. `@nx/maven` is guarded experimental; Maven Wrapper/reactor remains authority; pnpm owns the Nx/Node toolchain. | Canonical | Nx provides affected-work orchestration while Maven remains a direct, independently reproducible Java build. | Every Nx Maven target must prove a direct Maven equivalent; thin wrappers are the fallback if experimental inference breaks. | [16](16-monorepo-and-repository-structure.md), [19](19-versions-and-compatibility.md) |

| ADR-021 | Terraform owns AWS infrastructure, Helm packages workloads/add-ons, and Argo CD owns Kubernetes desired state; no resource has dual ownership. | Canonical | Separating account infrastructure, package definitions, and Git reconciliation prevents configuration drift and competing controllers. | Terraform must not manage Argo-owned workload resources; Helm must not become environment policy; Argo CD must not own AWS foundation. | [12](12-aws-production-platform.md), [13](13-ci-cd-and-gitops.md), [16](16-monorepo-and-repository-structure.md) |
| ADR-022 | Jenkins Configuration as Code is used for CI controller configuration; Ansible is excluded. Jenkins builds/publishes but does not deploy directly to production; Argo CD reconciles Git desired state. | Canonical | CI execution and production reconciliation need auditable, separate authorities. | Jenkins uses ephemeral agents and may propose a narrow digest update; it never runs direct production `kubectl apply` or stores secrets. | [12](12-aws-production-platform.md), [13](13-ci-cd-and-gitops.md) |
| ADR-023 | GitOps starts in the same repository on `main`, with environment directories; promote one immutable image digest, not environment branches or rebuilt images. | Canonical | A reviewed desired-state change and reconciliation history provide promotion provenance. | `dev`, `stage`, and `prod` composition is path-scoped; rollback selects a prior compatible digest/configuration. | [13](13-ci-cd-and-gitops.md), [16](16-monorepo-and-repository-structure.md) |
| ADR-024 | HPA scales HTTP/resource workloads, KEDA is staged for queue/lag work, managed node groups provide remote node capacity, and Karpenter is deferred. | Canonical | Pod resource scaling, queue-driven worker scaling, and node provisioning are different control loops. | HPA must not be presented as queue scaling; a node group is not a pod autoscaler; any Karpenter adoption needs a later comparison decision. | [11](11-local-development-platform.md), [12](12-aws-production-platform.md), [20](20-delivery-and-learning-roadmap.md) |
| ADR-025 | Local telemetry maps OTel/Prometheus/Loki/Tempo/Grafana to remote ADOT/AMP/CloudWatch Logs/X-Ray/Managed Grafana; metrics, logs, and traces remain distinct. | Canonical | Failure diagnosis needs complementary signals with separate data semantics. | Telemetry must be redacted, bounded, and non-authoritative; Promtail and the legacy X-Ray SDK/daemon are excluded. | [14](14-observability.md), [17](17-local-technology-stack.md), [18](18-remote-technology-stack.md) |

## Change discipline

Before changing a Canonical entry, a future decision record must identify the affected owner, data/contract boundary, migration and rollback path, compatibility impact, operational evidence, and whether the change turns a staged or excluded item into a baseline component. An Open choice is not permission to choose opportunistically; it is a gate with criteria in [22](22-exclusions-and-open-questions.md). Official source and Context7 validation expectations are in [23](23-primary-sources.md).
